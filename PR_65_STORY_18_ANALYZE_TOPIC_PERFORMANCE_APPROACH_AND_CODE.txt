1. EXECUTIVE SUMMARY & OBJECTIVES
--------------------------------------------------------------------------------
This PR fulfills all functional and non-functional requirements for Issue #18:
"STORY: Analyze Topic-Wise Performance".

User Story:
"As a student, I want to view my performance across different subjects and topics
so that I can identify areas requiring improvement."

Key Capabilities Delivered:
1. Topic-wise accuracy percentages calculated from completed individual quiz attempts.
2. Per-topic average time per question derived from persisted attempt timings.
3. Cohort percentile ranks per topic calculated across completed peer attempts.
4. Identification of strong, moderate, and weak topics with summary lists.
5. Optional subject-level filtering (`?subject=...`).
6. Server-side RBAC: students can only access their own analytics (403 for unauthorized
   cross-student access); moderators can inspect any student's performance.
7. Clean empty-state handling for accounts with zero completed attempts.
8. Sub-second response times (<600 ms, NFR-01) via SQLAlchemy selectinload eager-loading.

Acceptance Criteria Verification:
[X] AC1: Quiz questions are associated with subjects or topics.
    -> Question model links subject (e.g. "Software Engineering", "Mathematics")
       and topic (e.g. "Testing", "Algorithms", "Arithmetic").
[X] AC2: Topic-wise accuracy percentages are calculated from completed quiz attempts.
    -> Only attempts with status == AttemptStatus.COMPLETED are evaluated.
       Formula: (correct_answers / total_questions) * 100, rounded to 2 decimal places.
[X] AC3: Average time per question is calculated for the relevant topic data.
    -> Question timings are mapped per question ID within that specific topic.
       Formula: sum(timings) / count(timed_questions), rounded to 2 decimal places.
[X] AC4: Cohort percentile ranks are calculated where sufficient cohort data is available.
    -> Evaluates all peer students who completed questions in the same topic.
       Formula: 100 * (cohort members with accuracy <= student accuracy) / total cohort members.
[X] AC5: Students can identify relatively strong and weak topics.
    -> Each topic record contains strength_level: "strong" (>= 75%), "moderate" (50-74.99%),
       or "weak" (< 50%). Aggregated lists `strong_topics` and `weak_topics` are returned.
[X] AC6: Analytics are derived from completed individual quiz attempts.
    -> In-progress / active attempts are excluded until successfully finalized.
[X] AC7: Private student analytics are protected by server-side access controls.
    -> Current user defaults to their own metrics. Route /users/{student_id}/analytics/topics
       enforces current_user.id == student_id or current_user.role == UserRole.MODERATOR.
       Violations yield HTTP 403 Forbidden. Non-existent users yield HTTP 404 Not Found.

3. ARCHITECTURAL DESIGN & DATABASE ACCESS STRATEGY
--------------------------------------------------------------------------------
To satisfy NFR-01 (< 600 ms query latency for up to 1,000 attempts), we avoid
the classic N+1 query problem by using SQLAlchemy 2 `selectinload`:

```python
attempts = db.scalars(
    select(QuizAttempt)
    .options(
        selectinload(QuizAttempt.quiz)
        .selectinload(Quiz.questions)
        .selectinload(QuizQuestion.question)
    )
    .where(
        QuizAttempt.student_id == student_id,
        QuizAttempt.status == AttemptStatus.COMPLETED,
    )
    .order_by(QuizAttempt.completed_at.asc(), QuizAttempt.id.asc())
).all()
```

This batches the query into exactly 3 efficient SQL statements:
1. `SELECT * FROM quiz_attempts WHERE student_id = ... AND status = 'completed'`
2. `SELECT * FROM quizzes WHERE id IN (...)`
3. `SELECT * FROM quiz_questions JOIN questions ... WHERE quiz_id IN (...)`

Data aggregation is performed in-memory in O(N_questions) linear time.

4. SCHEMAS & DATA CONTRACTS ADDED
--------------------------------------------------------------------------------
In `backend/app/schemas.py`:

```python
class TopicPerformanceDetail(BaseModel):
    subject: str
    topic: str
    total_questions: int
    correct_answers: int
    accuracy_percentage: float
    average_time_seconds: float | None = None
    cohort_percentile: float | None = None
    strength_level: Literal["strong", "moderate", "weak"]


class TopicPerformanceResponse(BaseModel):
    student_id: int
    total_quizzes_evaluated: int
    total_questions_evaluated: int
    topics: list[TopicPerformanceDetail]
    strong_topics: list[str]
    weak_topics: list[str]
```

5. API ENDPOINTS IMPLEMENTED
--------------------------------------------------------------------------------
1. `GET /analytics/topics`
   `GET /analytics/topics/me`
   `GET /api/v1/analytics/topics`
   `GET /api/v1/analytics/topics/me`
   - Description: Retrieves topic-wise performance for the currently authenticated student.
   - Query Params: `subject` (optional, string) - filters topics by subject.
   - Auth: Bearer Token required.
   - Response: 200 OK with `TopicPerformanceResponse`.

2. `GET /users/{student_id}/analytics/topics`
   `GET /api/v1/users/{student_id}/analytics/topics`
   - Description: Retrieves topic-wise performance for a specific student.
   - Auth: Current student (self) or Moderator role required.
   - Status Codes:
     * 200 OK: Valid access.
     * 403 Forbidden: Attempt by unauthorized student to inspect another student's metrics.
     * 404 Not Found: Student ID does not exist in the database.
